\title{Is a Cached Token Worth It? Measuring the Energy Discount of Prefix Caching in LLM Serving\\[2pt]
\large Midterm Report}

\author{\IEEEauthorblockN{Aagam Sachin Bothara}
\IEEEauthorblockA{Department of Computer Science, University of Illinois Chicago\\
aboth@uic.edu}}

\maketitle

\begin{abstract}
On an A100, a cached prefix token costs under 0.4\% of a recomputed one, and enabling SGLang's radix cache costs nothing measurable when nothing is reused; output length, not prefix length, decides what fraction is saved. On held-out ShareGPT, agent, and RAG replays, cache-unaware energy accounting errs by 29--39\%; every cache-aware variant, by about 6--10\%.
\end{abstract}

\section{Project Type and Status}
An individual research project; the questions are unchanged. RQ1: how much GPU energy does reusing a cached prefix actually save in SGLang~\cite{sglang}? RQ2: does an accounting model with an explicit cached-token cost predict energy better than cache-unaware, pricing-inspired, and FLOP-informed baselines? Prior energy studies compare cache settings~\cite{zine,prefixbench}; this project separates the cost of reuse from the cost of having the cache enabled, and tests whether accounting models need a cached-token cost at all. \textbf{Status at Nov 1.} All planned measurements are done, including November's: the $D(L)$ grid, a second model and GPU, the zero-hit control, the vLLM reproduction, and the held-out RQ2 evaluation. What remains is one open RQ2 discrepancy, figures, the presentation, and the final report. The main change, answering feedback that cache on vs.\ off was unclear, is a precise definition of the conditions (Section~\ref{sec:conditions}).

\section{Clarifying the Experimental Conditions}
\label{sec:conditions}
``Cache on'' vs.\ ``off'' conflates whether the radix cache is enabled, whether a request's prefix is actually found in it, and side effects of the flag itself; Table~\ref{tab:cond} separates them. The per-request KV cache used in decoding stays on throughout; only cross-request reuse changes.

\textbf{Primary contrast: \textsc{Hit} vs.\ \textsc{Miss}.} Both run on the same server process with the same flags and token counts; only whether the prefix is found differs, so their gap is the value of reuse alone. I redefine the discount as
\begin{equation}
D(L) = \frac{E_{\textsc{miss}}(L) - E_{\textsc{hit}}(L)}{E_{\textsc{miss}}(L) - E_{\textsc{miss}}(0)},
\label{eq:d}
\end{equation}
where $E$ is mean active GPU energy per request, and suffix length, output length, and concurrency are held fixed. $E_{\textsc{miss}}(0)$ is measured with the prefix removed. I also report energy saved per reused token, $(E_{\textsc{miss}}(L)-E_{\textsc{hit}}(L))/L$.

\textbf{Secondary contrast: \textsc{Miss} vs.\ \textsc{Off}.} The zero-hit control, $\Delta_{\text{on}}(L)=E_{\textsc{miss}}(L)-E_{\textsc{off}}(L)$, is what enabling the cache costs when nothing is reused (insertion, matching, eviction), the effect Zine et al.~\cite{zine} saw on a workload with no repeated prefixes.

\textbf{Confounders held fixed.} (1) \emph{Scheduling policy.} With the radix cache disabled, SGLang silently replaces cache-aware policies such as LPM with FCFS (\texttt{\_validate\_and\_adjust\_policy}), so \textsc{Off} vs.\ \textsc{Hit} could compare two schedulers. I pin \texttt{-{}-schedule-policy fcfs} everywhere. (2) \emph{Exact token counts.} Requests are token IDs sent to \texttt{/generate} with no chat template; each suffix starts with a per-request unique token, so no spurious 1-token hits. (3) \emph{Fixed work.} \texttt{ignore\_eos} with fixed \texttt{max\_new\_tokens}, greedy decoding, fixed chunked-prefill size, page size 1, CUDA graphs on. (4) \emph{Cache state.} \texttt{/flush\_cache} before every window, then one excluded warm-up request in every condition (in \textsc{Hit} it inserts the prefix).

\textbf{Verification.} A window is accepted only if every response's \texttt{cached\_tokens} matches Table~\ref{tab:cond}. In all 1{,}016 synthetic windows (463{,}572 requests, both models, GPUs, and engines), every request matched.

\section{Measurement Setup as Built}
\textbf{Platform.} Chameleon Cloud had no A100 free in late October and its GPUs were reserved Nov 8--15, during the measurements planned for November, so the study runs on rented whole RunPod A100 80\,GB SXM4 GPUs (SGLang 0.5.21). All energy is GPU energy from NVML; CPU, host memory, and the rest of the server are not measured. In every A100 session, NVML's energy counter agreed with its instantaneous power reading at idle to within 0.5\,W. Clocks and power limit cannot be locked on a rented pod, so both are logged per window, and a fixed reference window opens every session. RunPod's A100 SXM4 pods come with either a 400\,W or a 500\,W limit; all A100 results below are from 400\,W cards (a Qwen3 session on a 500\,W card, with a 60.8\,J reference window, was rerun). Models: Qwen2.5-7B-Instruct and Qwen3-8B, BF16; second GPU: A40 (48\,GB).

\textbf{Harness.} A closed-loop load generator holds $c$ requests in flight over windows of at least 40 requests \emph{and} 30\,s (10 requests for 512-token outputs at $c{=}1$, where one takes 5--6\,s), reading NVML's cumulative energy counter at window boundaries. Active energy subtracts idle power (60\,s with the model loaded, before each block) times duration. Run order is randomized; each window logs SM clock, temperature, power limit, and other GPU processes. It also drives vLLM~0.11.0 and replays held-out workloads open-loop. Code and results: \url{https://github.com/Aagam-Bothara/prefix-cache-energy}.

\section{RQ1 Results}

\textbf{Noise floor.} Within a session, the reference \textsc{Miss} window ($L{=}2048$, out 1, $c{=}1$) varied by 0.3--0.9\% (CV of active energy per request); session means stayed within 45.4--45.9\,J (Qwen2.5) and 50.0--50.4\,J (Qwen3) across all 400\,W sessions.

\textbf{Zero-hit control.} In the first sweep, \textsc{Miss} and \textsc{Off} ran on two server processes, and $\Delta_{\text{on}}$ stayed within $+2.7\%$ of $E_{\textsc{off}}$. To separate this from restart effects, cache-on and cache-off servers then alternated over 8 ABBA rounds, each a fresh server with its own idle measurement (Welch $t$-intervals over round means), at $L\in\{0, 2048, 8192\}$ with (out 1, $c{=}1$) and (out 128, $c{=}4$). $|\Delta_{\text{on}}|$ was at most 0.1\% on SGLang and 0.3\% on vLLM, and every 95\% CI on both engines includes zero, so the ``turn caching on'' saving equals the reuse saving; the earlier +2.7\% was most likely a restart effect. Filling the cache is free too: with 128- or 512-token outputs at $c{=}1$, the \textsc{Hit} warm-up request that inserts the prefix cost within 1\% of a \textsc{Miss} warm-up at the same $L$ (1532 vs.\ 1533\,J at $L{=}8192$, out 512). A cached prefix therefore pays for itself on its first reuse.

\textbf{Discount curve.} With 1-token outputs, which isolate prefill, $E_{\textsc{miss}}$ grows from 15.6\,J ($L{=}512$) to 172.3\,J ($L{=}8192$) while $E_{\textsc{hit}}$ stays at 6.7--7.4\,J, so $D$ rises from 0.986 [0.980, 0.992] to 0.995 [0.995, 0.996] (Table~\ref{tab:grid}, first column). The saving is far outside the 0.9\% noise floor at every $L$. A pricing rule of $b=0.1a$~\cite{openai,anthropic} predicts $D\approx0.9$; the measured values are above this, since a cached token cost about 0.08\,mJ against about 20\,mJ for a recomputed one. The 20\,mJ is physically plausible: a fresh token needs about 14\,GFLOP ($2\times6.5$\,B parameters, plus attention), so even at the A100's 312\,TFLOPS BF16 peak, at these windows' 310\,W active power, it would cost about 14\,mJ; at $L\ge2048$ the windows ran at 190--220\,TFLOPS, 62--70\% of peak. Longer outputs lower $D$, because decoding still reads the prefix at equal cost in \textsc{Hit} and \textsc{Miss}: $D$ falls to 0.84--0.97 at 128 output tokens and 0.80--0.97 at 512. The energy saved per reused token stays between 0.016 and 0.028\,J in every cell; $D$ shrinks only because the rest of the request grows. \emph{When the saving becomes small:} in Eq.~2 (Section~\ref{sec:rq2}), reuse saves $(a-b)L$, while the denominator of Eq.~\ref{eq:d} is $aL + d\,n_{\text{out}}L$, since every output token also reads the prefix, so $D\approx a/(a+d\,n_{\text{out}})$, roughly independent of $L$. The fitted $a$ and $d$, pooled over all loads, put $D$ below 0.9 beyond about 200 output tokens on Qwen2.5 and 110 on Qwen3. The formula omits load, since $c_k$ cancels, but load matters: at 128 output tokens the saving per reused token barely changes from $c{=}1$ to $c{=}16$, while the rest of the denominator shrinks about threefold, so $D$ is 0.84--0.91 at $c{=}1$ and 0.95--0.97 at $c{=}16$. Measured $D$ was below 0.9 only at 128 tokens with $c{=}1$ and 512 with $c{=}4$.

\textbf{Where the saving comes from.} Mostly time, not power: at $L{=}8192$ with 1-token outputs, \textsc{Miss} and \textsc{Off} drew about 397\,W at about 1260\,MHz and \textsc{Hit} about 363\,W at the full 1410\,MHz, but each request finished far sooner. With 128 or 512 output tokens, all conditions held 1410\,MHz at 345--394\,W.

\textbf{Second model: Qwen3-8B.} At five load levels (out 1 at $c\in\{1,4\}$; out 128 at $c\in\{1,4,16\}$), the pattern is the same: $D$ is 0.979--0.997 with 1-token outputs and 0.80--0.96 with 128 output tokens. Each reused token saves 0.020--0.026\,J, 6--29\% more than on Qwen2.5-7B in the same cell (median 13\%).

\textbf{Second GPU: A40.} At $L\in\{2048, 8192\}$ with (out 1, $c{=}1$) and (out 128, $c{=}16$), the A40's $D$ matches the A100's to within 0.003, but the joules saved per reused token are 26--36\% higher (0.024--0.029\,J), so energy constants must be fitted per GPU.

\textbf{vLLM reproduction.} Following PrefixBench~\cite{prefixbench}, I sent sequential requests sharing an 8192-token prefix (3 windows of $\ge$40 requests and $\ge$30\,s) to one vLLM~0.11.0 server with prefix caching and one with \texttt{-{}-no-enable-prefix-caching}, serving Qwen2.5-7B. This single pair was not repeated, so there is no CI over servers. Cache on with reuse vs.\ off saves 97.3\% for 1-token outputs (176.2\,J $\to$ 4.7\,J per request) and 33.6\% for 128-token outputs (541.6\,J $\to$ 359.4\,J). The per-token saving (0.021\,J) and $D$ (0.995 and 0.928) match SGLang closely. PrefixBench reports 443 vs.\ 337\,J per request on an H100 (Qwen2-7B, same prefix), a 24\% saving, without stating the output length, so the comparison is only qualitative. This run's \textsc{Miss} vs.\ \textsc{Off} gap ($-0.4\%$ to $-1.7\%$) would echo Zine et al.~\cite{zine}, but alternating rounds put vLLM's $\Delta_{\text{on}}$ at $-0.3\%$ to $0.0\%$: most likely a restart effect too.

\section{RQ2 Results: Accounting Models}
\label{sec:rq2}
\textbf{Model.} All four variants are Eq.~2 of the proposal,
\begin{equation}
\hat E = a\,n_{\text{fresh}} + b\,n_{\text{cached}} + c_k\,n_{\text{out}} + d\,n_{\text{out}}\,n_{\text{ctx}},
\end{equation}
with $n_{\text{ctx}}$ the mean context during decoding (prompt plus half the output). They differ only in the prefill part: \emph{explicit} fits $a$ and $b$ freely; \emph{cache-unaware} forces $b=a$; \emph{pricing} forces $b=0.1a$; \emph{FLOP-informed} replaces $a\,n_{\text{fresh}}+b\,n_{\text{cached}}$ by $k$ times the remaining prefill FLOPs. The load term, one $c_k$ per fitted concurrency $k$ interpolated in $\log k$, reflects batching sharing a decode step's weight reads; without it every variant errs by over 65\%. Coefficients are fitted by least squares on synthetic windows only (387 over 9 load levels for Qwen2.5, 201 over 5 for Qwen3).

\textbf{Held-out workloads.} ShareGPT conversations (mean prompt 684 tokens, output 257); agent requests sharing one of four $\sim$3{,}000-token tool prompts (3{,}110, 73); and RAG questions over Zipf-popular LongBench documents (5{,}493, 21). Each has 3 windows of 120 requests, replayed open-loop from an empty cache with fixed-rate and Poisson arrivals at 1 and 4 requests/s: 36 windows per model, 56--96\% of prompt tokens cached. A window's prediction sums per-request estimates, each at its own load.

\textbf{Findings.} (1) Ignoring the cache is clearly wrong. On held-out windows, explicit's error is 10.3\% vs.\ 29.2\% for cache-unaware on Qwen2.5 and 6.4\% vs.\ 38.9\% on Qwen3. Both give $p=2/512\approx0.004$, the minimum for an exact paired sign-flip test over 9 replay blocks. This is RQ2's primary comparison; the tests among cache-aware variants below are exploratory. (2) A cached token's fitted cost is near zero: $b=-0.36$\,mJ (95\% bootstrap CI over windows [$-0.67$, $-0.10$]) against $a=20.9$\,mJ per fresh token on Qwen2.5, and $b=-0.07$\,mJ ([$-0.33$, $+0.14$]) against $a=23.4$\,mJ on Qwen3. A negative cost is unphysical (other terms likely absorb a small effect), but $|b|<2\%$ of $a$ either way, and RQ1's direct 0.08\,mJ is under 0.4\%. A cached token is much closer to free than the 10\% that API pricing commonly charges~\cite{openai,anthropic}. (3) The cache-aware variants are close. On Qwen2.5, FLOP-informed beats explicit by 1.0 point ($p=0.004$) and pricing beats it by 3.3 ($p=0.020$); on Qwen3, neither difference is clear ($p=0.44$ and $0.09$). FLOP-informed has no cached-token parameter yet does at least as well as fitting $b$: counting the prefill FLOPs executed suffices, so a cached token's cost need not be measured. Synthetic errors are larger because 1-token \textsc{Hit} windows cost only a few joules. (4) Explicit and FLOP-informed underpredict RAG at 1 request/s by 19--30\% on both models, against mostly 1--10\% on agent and ShareGPT; pricing's cached-token charge happens to offset this, and a per-request constant does not remove it. My hypothesis: RAG reuses many cached documents; synthetic \textsc{Hit} windows reuse one.

\section{Changes from the Proposal}
RQs, baselines, and Eq.~2 are unchanged. (1)--(2) The conditions and controls of Section~\ref{sec:conditions}. (3) The platform moved from Chameleon Cloud to RunPod A100s, for the reason given above; RunPod has no A30, so the second GPU is an A40. (4) Qwen3-8B replaces Llama-3.1-8B-Instruct: close in size, no gated-model access. (5) NVML's energy counter is read directly instead of through llmtrace, which samples power and supports only vLLM.
